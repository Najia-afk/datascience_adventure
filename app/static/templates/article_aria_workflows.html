The Autonomous Work Cycle

At 03:15 on a Tuesday, while everyone sleeps, Aria wakes up. She checks her goals, picks the most urgent one, delegates it to her best-performing agent, executes exactly one action, writes the result to memory, and goes back to sleep. Fifteen minutes later, she does it again. This is the work cycle—the smallest unit of autonomy. It's goal-driven, not static: the action she chooses depends on what matters right now.

📋

1. Context Loading

Read active_focus_level and active_goal_reference from working memory. Focus level determines how many goals to load: L1=1, L2=3, L3=5.

🎯

2. Priority Selection

Fetch in-progress goals, rank by urgency and strategic importance. Pick the single highest-priority actionable goal. One action per cycle.

🧠

3. Agent Routing

Pheromone scoring selects the best agent for the task. Score = success_rate × 0.6 + speed × 0.3 + cost × 0.1. Daily decay of 0.95.

⚡

4. Skill Execution

Execute exactly one concrete action via the selected agent's skill set. Budget: max 10 tool calls per cycle. Circuit breaker halts if API fails.

📝

5. Progress Update

Update goal progress, refresh active_goal_reference in working memory. Write artifact to aria_memories/logs/. Log to activity_log table.

🧹

6. Session Cleanup

Prune stale sessions (>24h). Archive completed work. If circuit breaker tripped, write degraded artifact and halt gracefully.

YAML Pipelines — DAG-Executed Skill Composition

A work cycle does one thing. A pipeline does many things in the right order. Each YAML file describes a multi-step workflow as a directed acyclic graph—skills chained by dependency, validated for cycles before a single step executes, then run with parallel branches via asyncio.gather(). One step's output becomes the next step's input through {{context.step_name.field}} templates. If a step fails, the pipeline doesn't just crash—it follows a declared strategy: stop, skip, retry, or fall back to an alternative skill.

aria_skills/pipelines/daily_research.yaml
name: daily_research steps: - name: check_goals skill: goals method: get_active_goals depends_on: [] on_failure: stop - name: research skill: research method: deep_search params: topics: "{{context.check_goals.focus_areas}}" depends_on: [check_goals] on_failure: retry:2 - name: analyze skill: pattern_recognition method: analyze_findings depends_on: [research] on_failure: skip - name: save_report skill: memory_compression method: store_summary depends_on: [analyze] - name: post_summary skill: social method: share_insight depends_on: [save_report] on_failure: fallback:moltbook.draft_post

Pipeline Execution Engine

The brain of the pipeline system lives in pipeline_executor.py. Before any skill fires, it verifies the graph is acyclic, sorts it, and plans execution waves. Four mechanisms keep things honest:

📐

Kahn's Algorithm

Topological sort with cycle detection. If a cycle exists, the pipeline is rejected before any step executes. Guarantees deterministic ordering.

⚡

Parallel Waves

Independent branches execute concurrently via asyncio.gather(). Steps only wait for their declared depends_on set.

🔄

Failure Strategies

stop — halt entire pipeline. skip — mark step as skipped, continue. retry:N — retry N times. fallback:skill.method — run alternative.

🔗

Template Resolution

Parameters support {{context.step.field}} templates, resolved at runtime from prior step outputs. Enables dynamic data flow across the pipeline.

The Knowledge Graph — Two Graphs, One Database

Aria doesn't just store facts—she maps the connections between them. Two knowledge graphs live in PostgreSQL, each with a fundamentally different personality. One grows organically from things Aria discovers during research and conversation. The other is engineered: auto-generated from 41 skill manifests every time a new capability is deployed. One is nature; the other is architecture. Both use the same entity/relation schema, and both can be traversed through the API.

🌱

Organic Knowledge Graph

Entities discovered during research, conversations, and analysis. Tables: knowledge_entities + knowledge_relations. Grows naturally over time. BFS traversal via /kg-traverse. JSONB properties on every node and edge.

🌳

Skill Graph

Auto-generated from 41 skill.json manifests via generate_skill_graph.py. Tables: skill_graph_entities + skill_graph_relations. Regenerated idempotently. Separate from organic KG.

Session Isolation — Every Workflow Gets Its Own Context

The Midnight Cascade taught a painful lesson: when agents share state, one agent's failure becomes every agent's failure. Aria's answer is session isolation—every cron job, every roundtable, every pipeline runs in its own sandbox. Sessions are created per conversation or per cron execution, typed as interactive, cron, or subagent, each tracking its own token counts, cost, message history, and active model.

A research run cannot leak into a security scan. A morning planning session cannot contaminate an unrelated pipeline. This is the architectural equivalent of good fences make good neighbors—strict isolation boundaries for state, history, and cost tracking that make true parallelism safe.

Every session is its own world. Token counts, model assignments, cost—all scoped. No bleed.

Pheromone Scoring — Bio-Inspired Agent Routing

How does Aria decide which of her seven agents should handle a task? Not with a lookup table. Not with hardcoded rules. She uses pheromone scoring—a technique borrowed from ant-colony optimization where past success leaves invisible trails that guide future decisions. Agents that deliver earn stronger pheromone. Agents that fail see theirs fade.

aria_agents/scoring.py
from datetime import datetime, timedelta from typing import Optional DECAY_RATE = 0.95 # Applied daily; 0.95^7 ≈ 0.70 after one silent week W_SUCCESS = 0.6 W_SPEED = 0.3 W_COST = 0.1 def pheromone_score(agent, as_of: Optional[datetime] = None) -> float: """Weighted composite with time-decay. Higher = route more work here.""" raw = ( agent.success_rate * W_SUCCESS + agent.speed_score * W_SPEED + agent.cost_efficiency * W_COST ) as_of = as_of or datetime.utcnow() days_idle = (as_of - agent.last_completed_at).total_seconds() / 86400 return raw * (DECAY_RATE ** days_idle) def select_best_agent(task, agents, as_of=None): """Pick the highest-pheromone agent whose skill set covers the task.""" candidates = [ a for a in agents if task.domain in a.skill_domains and not a.is_suspended ] if not candidates: raise NoEligibleAgentError(task.domain) return max(candidates, key=lambda a: pheromone_score(a, as_of))

The 0.95 daily decay is the quiet genius of the system. Without it, a single agent could dominate forever on the strength of early wins. With it, yesterday's hero has to keep proving itself. A 95% success rate today decays to 77% in a week if the agent goes silent. Fall behind, and the pheromone trail naturally redirects work to whoever's delivering now.

Roundtable vs. Swarm — Collective Intelligence

Some problems are too wide for one perspective. When a security audit touches infrastructure, data architecture, and social reputation simultaneously, no single agent has the full picture. Aria solves this with two collaboration protocols—one for structured debate, one for emergent consensus:

Three rounds of structured debate. Every agent contributes. The synthesizer has the last word.
🏛️

Roundtable Protocol

3 structured rounds. All agents respond in parallel via asyncio.TaskGroup. Each round sees prior context. A designated synthesizer produces the final answer. Max 5 agents, 60s per-agent timeout, 300s total timeout. Triggered by /roundtable, REST API, or weekly cron.

🐝

Swarm Protocol

Iterative convergence (max 5 iterations). Each agent votes: agree|disagree|extend|pivot with confidence 0.0–1.0. Pheromone-weighted voting. Consensus at ≥70% agreement. Stigmergy pattern: each agent reads the prior trail. 2–12 agents.

Self-Healing — 4-Phase Error Recovery

Things break. APIs go down. Models hallucinate. Databases lock. The question isn't whether failure happens—it's whether the system degrades gracefully or cascades catastrophically. The Midnight Cascade was the catastrophic version. These four phases are the answer:

🔁

Phase 1: API Circuit Breaker

Exponential backoff + jitter in api_client. All 112 endpoint methods delegate to _request_with_retry(). Brief failures recover automatically.

🔀

Phase 2: LLM Fallback Chain

qwen3-mlx (local) → trinity-free → qwen3-next-free → deepseek-free → kimi (paid, last resort).

📉

Phase 3: Health Degradation

HEALTHY → DEGRADED (suspend social/moltbook) → CRITICAL (suspend research/brainstorm/goals). Heartbeat + health_check never suspend.

📝

Phase 4: Degraded Artifact

If circuit breaker fully opens, the work cycle writes a degraded artifact explaining what failed and halts gracefully. No silent failures. Every stop is documented.

What the Workflow Engine Actually Is

Not a scheduler. Not a task queue. Not a glorified cron wrapper. Aria's workflow engine is a coordinated runtime—cron jobs, work cycles, YAML pipelines, delegation logic, and memory systems operating as one continuous control loop. The scheduler triggers the cycle. The cycle consults memory. Memory informs the goal. The goal selects the agent. The agent executes. The execution feeds back into memory. Remove any piece and the loop breaks.

The Three Timescales

Every system has a clock. Aria has three:

  1. Real-time (seconds) — Interactive chat, WebSocket sessions, immediate tool calls. Human-triggered, Aria-executed. This is the conversational layer, the part that feels like talking to someone.
  2. Operational (minutes) — Work cycles every 15 minutes. Single goal, single action, single artifact. The heartbeat of autonomy. This is where most of Aria's work happens—quietly, at 3 AM, with no audience.
  3. Strategic (hours/days) — Six-hour reviews, daily reflections, weekly summaries, memory consolidation. This is the thinking layer—where Aria steps back, looks at the trajectory, and adjusts course.

Why PostgreSQL for Everything

This is the decision most architects would argue against. Vectors in PostgreSQL? Graphs in PostgreSQL? Scheduler state in PostgreSQL? The answer is transactional consistency. When a work cycle updates a goal, writes an artifact, logs telemetry, and stores a memory, all of that commits in one transaction—or none of it does. No eventual consistency. No orphaned writes. The price is a single point of failure. The reward is a system that never lies about its own state.

The Automation Gradient

Not everything should be autonomous. The gradient is deliberate:

  • Fully autonomous: work_cycle, db_maintenance, session_cleanup, nightly_tests, memory_bridge — the maintenance layer that should never need human attention
  • Autonomous with review: daily_reflection, weekly_summary, social_engagement — Aria writes, Najia reads
  • Consent-gated: External publishing, destructive operations, raw SQL — Aria proposes, Najia approves
  • Human-triggered: Interactive chat, /roundtable, /swarm, manual pipeline runs — Najia initiates, Aria executes
“A chatbot reacts to what you say. A workflow engine acts on what it believes needs doing. The difference isn't intelligence—it's initiative.”

A script runs when you call it. A cron job runs on schedule. A workflow engine does something harder: it decides what to run, who should run it, and whether the result was good enough—then remembers the answer for next time.

6 DAG pipelines. 12 cron jobs. 768-dimensional memory. Dual knowledge graphs. Pheromone-scored delegation. 50 Prometheus metrics. One PostgreSQL instance. One 15-minute heartbeat. No human in the loop at 3 AM.

This is what autonomy actually looks like—not freedom from structure, but freedom through it. ⚡️
