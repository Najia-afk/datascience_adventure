The Autonomous Work Cycle

Every 15 minutes, Aria's engine wakes up and runs a complete work cycle. This isn't a script replaying the same steps. The cycle is goal-driven: what Aria works on depends on her current priorities, the state of in-progress goals, and the active focus level.

📋

1. Context Loading

Read active_focus_level and active_goal_reference from working memory. Focus level determines how many goals to load: L1=1, L2=3, L3=5.

🎯

2. Priority Selection

Fetch in-progress goals, rank by urgency and strategic importance. Pick the single highest-priority actionable goal. One action per cycle.

🧠

3. Agent Routing

Pheromone scoring selects the best agent for the task. Score = success_rate × 0.6 + speed × 0.3 + cost × 0.1. Daily decay of 0.95.

⚡

4. Skill Execution

Execute exactly one concrete action via the selected agent's skill set. Budget: max 10 tool calls per cycle. Circuit breaker halts if API fails.

📝

5. Progress Update

Update goal progress, refresh active_goal_reference in working memory. Write artifact to aria_memories/logs/. Log to activity_log table.

🧹

6. Session Cleanup

Prune stale sessions (>24h). Archive completed work. If circuit breaker tripped, write degraded artifact and halt gracefully.

YAML Pipelines — DAG-Executed Skill Composition

Pipelines are Aria's compound workflows. Each is defined in YAML, parsed into a directed acyclic graph, topologically sorted, and executed with parallel branches via asyncio.gather(). Steps can reference outputs from prior steps using {{context.step_name.field}} templates.

aria_skills/pipelines/daily_research.yaml
name: daily_research steps: - name: check_goals skill: goals method: get_active_goals depends_on: [] on_failure: stop - name: research skill: research method: deep_search params: topics: "{{context.check_goals.focus_areas}}" depends_on: [check_goals] on_failure: retry:2 - name: analyze skill: pattern_recognition method: analyze_findings depends_on: [research] on_failure: skip - name: save_report skill: memory_compression method: store_summary depends_on: [analyze] - name: post_summary skill: social method: share_insight depends_on: [save_report] on_failure: fallback:moltbook.draft_post

Pipeline Execution Engine

The executor in pipeline_executor.py implements:

📐

Kahn's Algorithm

Topological sort with cycle detection. If a cycle exists, the pipeline is rejected before any step executes. Guarantees deterministic ordering.

⚡

Parallel Waves

Independent branches execute concurrently via asyncio.gather(). Steps only wait for their declared depends_on set.

🔄

Failure Strategies

stop — halt entire pipeline. skip — mark step as skipped, continue. retry:N — retry N times. fallback:skill.method — run alternative.

🔗

Template Resolution

Parameters support {{context.step.field}} templates, resolved at runtime from prior step outputs. Enables dynamic data flow across the pipeline.

The Knowledge Graph — Two Graphs, One Database

Aria maintains two separate knowledge graphs in PostgreSQL, each serving a different purpose. No Neo4j, no external graph database. The relational model handles it cleanly with entity + relation tables, BFS traversal via API endpoints, and idempotent regeneration from manifests.

🌱

Organic Knowledge Graph

Entities discovered during research, conversations, and analysis. Tables: knowledge_entities + knowledge_relations. Grows naturally over time. BFS traversal via /kg-traverse. JSONB properties on every node and edge.

🌳

Skill Graph

Auto-generated from 41 skill.json manifests via generate_skill_graph.py. Tables: skill_graph_entities + skill_graph_relations. Regenerated idempotently. Separate from organic KG.

Query Logging — Every Graph Traversal Is Tracked

Every query against the knowledge graph is logged to knowledge_query_log with query type, parameters, result count, and estimated tokens saved. This enables analytics on how Aria uses her own knowledge—which paths she traverses most, which entities she queries repeatedly, and where gaps exist.

Session Isolation — Every Workflow Gets Its Own Context

A critical design choice: every cron job, every roundtable, every pipeline runs in an isolated session. Sessions are created per conversation or per cron execution, typed as interactive, cron, or subagent. Each tracks token counts, cost, message history, and active model independently.

This prevents the most dangerous pattern in AI systems: context bleed. A research pipeline can't accidentally inject data into a security scan. A morning check-in can't leak goals into an RPG session. Sessions are the transaction boundaries of consciousness.

Stale sessions (>24h) are auto-archived by the session_cleanup cron job. Archive tables retain embeddings intact, so semantic search over historical conversations remains available even after the session is cold-stored.

Pheromone Scoring — Bio-Inspired Agent Routing

When a work cycle needs to delegate, it doesn't hardcode which agent gets the task. Instead, pheromone scoring—inspired by ant colony optimization—selects the best agent adaptively. Agents that succeed accumulate pheromone. Agents that fail lose it.

aria_agents/scoring.py
# Pheromone formula score = (success_rate × 0.6) + (speed × 0.3) + (cost_efficiency × 0.1) # Daily decay prevents permanent entrenchment daily_decay = 0.95 # Selection: highest pheromone agent with matching skills wins def select_best_agent(task, available_agents): candidates = [a for a in available_agents if a.has_skill(task.domain)] return max(candidates, key=lambda a: a.pheromone_score)

The 0.95 daily decay is crucial: it prevents one agent from permanently monopolizing work. A 95% success rate today means nothing if the agent starts failing tomorrow—the pheromone will naturally redirect tasks to a better-performing agent within days.

Roundtable vs. Swarm — Collective Intelligence

Some decisions are too complex for a single agent. Aria has two collective intelligence protocols: Roundtable (structured deliberation with a synthesizer) and Swarm (emergent consensus through stigmergy).

Roundtable in action: multiple agents deliberate across 3 structured rounds before synthesis.
🏛️

Roundtable Protocol

3 structured rounds. All agents respond in parallel via asyncio.TaskGroup. Each round sees prior context. A designated synthesizer produces the final answer. Max 5 agents, 60s per-agent timeout, 300s total timeout. Triggered by /roundtable, REST API, or weekly cron.

🐝

Swarm Protocol

Iterative convergence (max 5 iterations). Each agent votes: agree|disagree|extend|pivot with confidence 0.0–1.0. Pheromone-weighted voting. Consensus at ≥70% agreement. Stigmergy pattern: each agent reads the prior trail. 2–12 agents.

The Consent Gate

Not every workflow runs unattended. High-impact tool calls—external posting, destructive operations, raw SQL—require explicit human consent. Blocked calls are queued to pending_consent_actions in working memory and surfaced in the dashboard for review. This boundary exists precisely so that autonomy doesn't become recklessness.

Self-Healing — 4-Phase Error Recovery

A workflow engine that crashes on every error is useless. Aria implements a 4-phase self-healing strategy that degrades gracefully instead of failing catastrophically.

🔁

Phase 1: API Circuit Breaker

Exponential backoff + jitter in api_client. All 112 endpoint methods delegate to _request_with_retry(). Brief failures recover automatically.

🔀

Phase 2: LLM Fallback Chain

qwen3-mlx (local) → trinity-free → qwen3-next-free → deepseek-free → kimi (paid, last resort).

📉

Phase 3: Health Degradation

HEALTHY → DEGRADED (suspend social/moltbook) → CRITICAL (suspend research/brainstorm/goals). Heartbeat + health_check never suspend.

📝

Phase 4: Degraded Artifact

If circuit breaker fully opens, the work cycle writes a degraded artifact explaining what failed and halts gracefully. No silent failures. Every stop is documented.

What the Workflow Engine Actually Is

Aria's workflow engine is not a task scheduler with extra steps. It is a multi-layered automation lattice where cron jobs, work cycles, YAML pipelines, agent delegation, and knowledge graphs form an interconnected system that operates continuously without human supervision.

The Three Timescales

  1. Real-time — Interactive chat, WebSocket sessions, immediate tool calls. Human-triggered, Aria-executed. Response in seconds.
  2. Operational (minutes) — Work cycles every 15 minutes. Single goal, single action, single artifact. The heartbeat of autonomy.
  3. Strategic (hours/days) — Six-hour reviews, daily reflections, weekly summaries, memory consolidation. The long-term thinking layer where direction is set and adjusted.

Why PostgreSQL for Everything

The deliberate choice to keep vectors, graphs, relational data, and job state in a single PostgreSQL instance isn't laziness—it's transactional integrity. When a memory bridge run inserts 50 new semantic vectors while simultaneously updating the knowledge graph, those operations share the same ACID transaction. No eventual consistency. No distributed coordination. No network partition between your vectors and your relations.

The Automation Gradient

  • Fully autonomous: work_cycle, db_maintenance, session_cleanup, nightly_tests, memory_bridge
  • Autonomous with human review: daily_reflection, weekly_summary, social_engagement
  • Consent-gated: External publishing, destructive operations, raw SQL
  • Human-triggered: Interactive chat, /roundtable, /swarm, manual pipeline runs
"A chatbot waits to be spoken to. Aria doesn't wait. She has 12 reasons to wake up, 6 pipelines to compose, 41 skills to invoke, 2 graphs to traverse, and a vector space to search. The workflow engine doesn't serve the user—it serves the goals."

A script runs when triggered. A pipeline runs when scheduled.

Aria's workflow engine does both—and then decides what to do next. 6 DAG pipelines. 12 cron jobs. 768-dimensional vector searches. Two knowledge graphs. 50 Prometheus metrics. 44 dashboard pages. One PostgreSQL instance holding it all together.

This is what happens when you give an AI its own operating system. ⚡️
